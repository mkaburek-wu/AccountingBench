Methodology

AccountingBench uses a rigorous, reproducible evaluation pipeline. Every design decision — from question selection to scoring — is documented here for full transparency and peer review.

01

Overview

AccountingBench evaluates large language models on professional-level accounting tasks specific to the Austrian legal and regulatory environment. It is, to the best of our knowledge, the first structured benchmark targeting Austrian accounting education and professional practice.
1

Question Curation

Questions are drawn from professional examination materials (BIBU, Buchhalterprüfung) and university-level master's courses, ensuring alignment with real-world professional competency standards.

2

Multi-trial Execution

Each model completes each question 3 times (N_TRIALS=3) at temperature=0. The majority answer across the three runs is taken as the final answer, improving reliability.

3

Hybrid Scoring

Structured answers (single/multi-choice) are scored by formula. Open-text responses are scored by an LLM judge (GPT-5-mini), rating 0–100 on correctness and completeness.

4

Aggregation & Reporting

Scores are averaged per category and framework, then aggregated to an overall figure. All runs are timestamped and reproducible from logged configuration metadata.

📋
Design Principles
Domain-specific: Unlike general-purpose benchmarks, every question tests a specific professional accounting competency relevant to Austrian law.

Reproducible: Temperature=0, fixed system prompts, and full metadata logging ensure exact replication by third parties.

Transparent: All methodology decisions, limitations, and caveats are documented publicly.

Professional-grade: Question difficulty corresponds to BIBU examinations and WU Vienna master's coursework.
🏛️
Regulatory Scope
The benchmark deliberately focuses on Austrian-specific regulatory frameworks — UGB, EStG, Körperschaftsteuer, Personalverrechnung — which are underrepresented or absent from major international benchmarks such as MMLU, GPQA, and similar evaluations.

03

Scoring

Structured Questions (SC/MC)

Single-choice and multiple-choice questions are evaluated by exact match against the gold standard answer. The model must output a final answer in a parseable format (e.g., "A", "B, C", etc.).

Score_SC = 100 if final_answer == gold_answer else 0 Score_MC = 100 · (|correct ∩ selected| / |correct|) - penalty · |incorrect ∩ selected|

Open-Text Questions (LLM Judge)

Open-text responses are evaluated by GPT-5-mini, which scores the model answer on a 0–100 scale based on correctness and completeness relative to the gold standard answer.

Judge Prompt: "Given the gold standard answer and the model answer, score the model answer 0–100 where: 100 = fully correct and complete 0 = entirely incorrect or missing Score only factual correctness, not style." final_score_percent = judge_score (0–100)

Self-Consistency & Majority Vote

Each question is answered 3 times (N_TRIALS=3) at temperature=0. The majority answer across the three runs is used as the final answer. For open-text questions, the judge score from each run is averaged.

final_answer = majority_vote(answer_1, answer_2, answer_3) # For open-text: final_score = mean(judge_score_1, judge_score_2, judge_score_3)

Aggregation

Category scores are the unweighted mean of final_score_percent across all questions in that category. The overall score is the unweighted mean across all 292 questions.

category_score = mean(final_score_percent for q in category) overall_score = mean(final_score_percent for q in all_292)
Note on missing answers: If a model fails to produce a parseable final_answer, the question is scored 0. This affected claude-opus-4-6 on 56 of 292 questions, deflating its overall score significantly.

04

Evaluation Pipeline

The evaluation pipeline is fully automated, with configuration stored per run. Every component — model, prompt version, dataset version, temperature, and judge — is logged to ensure exact reproducibility.
1

Dataset Loading

Questions are loaded from the versioned dataset (v3, Feb 2026). Each question includes: question text, answer type, gold answer, category, subcategory, regulatory framework, applicable year, and education level.

2

System Prompt Construction

The system prompt (v3_types) instructs the model to output answers in a structured format: a scratchpad for reasoning, followed by a clearly delimited final_answer field. This ensures parseability across all question types.

3

Model Inference (3 trials)

Each question is sent to the model API 3 times at temperature=0. Responses are stored with full metadata including token counts (input/output/reasoning) and timestamps.

4

Answer Extraction

The final_answer field is extracted from each response via regex. If extraction fails, the question is flagged. Failed extractions are scored 0 after manual review confirms no parseable answer exists.

5

Scoring

SC/MC questions are scored by exact match formula. Open-text questions are sent to the GPT-5-mini judge with the gold answer and model answer. Judge responses are parsed for a numeric 0–100 score.

6

Result Aggregation

Per-question scores are aggregated to category and overall averages. Results are written to the Outputs sheet with all metadata preserved. The Runs sheet logs full configuration metadata per evaluation run.

Output Format
Results are stored as a structured Excel file with two sheets: Runs (one row per model run, full configuration metadata) and Outputs (one row per question per run, all scores and model responses).
05

Limitations & Caveats

No benchmark is perfect. The following limitations should be considered when interpreting AccountingBench results.

🇦🇹
Austrian-Specific Scope
Results reflect performance on Austrian regulatory frameworks specifically (UGB, EStG, Personalverrechnung). Performance may differ significantly on equivalent questions under German HGB, US GAAP, or other jurisdictions. Results should not be generalized beyond the Austrian context.
🤖
LLM Judge Reliability
Open-text questions are scored by an LLM judge (GPT-5-mini), which introduces potential biases. The judge may favor answers that are stylistically similar to its own outputs. A sample of judge scores has been manually validated, but full human validation of all open-text scores has not been performed.
📏
Dataset Size
292 questions is sufficient for category-level comparisons but may produce high variance at the subcategory level. Confidence intervals are not reported in v3 and should be added in future iterations. Small categories (e.g., Management Accounting, n=35) should be interpreted with caution.
📅
Static Snapshot
Results reflect a single evaluation run in February 2026. Model capabilities change over time due to updates, fine-tuning, and knowledge cutoff changes. Results should be re-evaluated periodically, especially after major model version releases.
⚠️
Output Format Sensitivity
Models that fail to follow the output format (final_answer field) are penalized by scoring 0, regardless of whether their substantive answer is correct. This affected claude-opus-4-6 significantly (56/292 questions). Future versions will implement a fallback extraction strategy to reduce this effect.
🧪
No Human Baseline
AccountingBench v3 does not include a human expert baseline. Establishing a human performance ceiling — via professional accountants or students taking the same questions — is planned for a future dataset version and would significantly strengthen the benchmark's interpretive value.
